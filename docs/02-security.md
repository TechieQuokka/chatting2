# 보안

## 핵심 원칙

- 네트워크를 뚫어도 키 없이는 데이터를 읽을 수 없음
- 방 접근은 오직 초대 기반 — 초대받지 않은 사람은 방 키를 얻을 수 없음
- 모든 로컬 데이터는 계정 PW로 암호화 저장
- 모든 초대, 승인, 전송 행위는 로그에 기록됨

## 암호화 구조

| 대상 | 방식 |
|------|------|
| 방 키 | 방 생성 시 랜덤 생성 (AES-256-GCM) |
| 방 키 전달 | 초대 시 request-response로 1:1 전달 (libp2p Noise 암호화) |
| 채팅 메시지 | 방 키로 AES-256-GCM 암호화 |
| 파일 메타데이터 | 방 키로 AES-256-GCM 암호화 |
| 파일 청크 | 방 키로 AES-256-GCM 암호화 |
| 로컬 config | 계정 PW → Argon2id → AES-256-GCM 암호화 |

## 위협 모델

| 위협 | 방어 수단 | 비고 |
|------|----------|------|
| 네트워크 도청 | Noise(전송 구간) + AES-256-GCM(방 키) | 방 키 없이 복호화 불가 |
| 로컬 기기 탈취 | Argon2id + AES-256-GCM (rooms.enc) | 계정 PW 없이 방 키 접근 불가 |
| 방 키 유출 후 소급 복호화 | 미방어 (Forward Secrecy 미적용) | 방 수명 설정으로 노출 기간 제한 |

## 방 키 정책

- 방 키는 방 생성 시 한 번 생성되고 고정
- Forward Secrecy 미적용 — 방 키가 유출(계정 PW 탈취 등)된 경우 해당 방의 과거 트래픽 소급 복호화 가능
- 방 수명 설정으로 키 노출 위험 기간 제한 (기본 1일, 최대 무제한)
- 방 삭제 또는 수명 만료 시 방 키 포함 모든 관련 데이터 제거

## 로그 기록 대상

- 초대 코드 생성
- 초대 코드 사용 시도 (성공/실패)
- 입장 승인 / 거절
- 파일 공유 시작 / 철회
- 피어 연결 / 해제

## AES-256-GCM Nonce 관리

- 암호화마다 CSPRNG로 96비트(12바이트) 랜덤 nonce 생성
- 저장/전송 포맷: `nonce(12B) || ciphertext`
- 수신측은 앞 12바이트를 nonce로, 나머지를 ciphertext로 분리하여 복호화
- nonce 충돌 확률: 생일 역설 기준 2^48 ≈ 281조 회 암호화 시 50% → 현실적으로 도달 불가
- 피어 간 nonce 동기화 불필요

## AES-256-GCM 성능

- 현대 CPU의 AES-NI 하드웨어 가속으로 초당 수 GB 처리 가능
- 네트워크 대역폭이 항상 병목 — 암호화 비용은 무시할 수준
