# 설계 결정 기록

설계 문서 논리 결함 검토 후 확정된 결정 사항 목록.
각 항목은 문제 → 결정 → 반영 파일 순으로 기술.

---

## 높음 심각도

### D-01. 잠금 파일 비정상 종료 시 stale 처리

**문제:** 앱 크래시 시 잠금 파일이 해제되지 않아 다음 실행 시 "이미 실행 중" 오류 영구 발생.

**결정:** PID 파일 방식 + 수동 해제 안내 병행
- 잠금 파일(`~/.chatapp/lock`)에 현재 PID 저장
- 실행 시 PID 생존 여부 OS 확인 → stale이면 교체 후 정상 실행
- PID 확인 실패 시 수동 해제 안내 출력

**반영:** `03-account.md`, `12-tui.md`

---

### D-02. 비밀번호 변경 중 크래시 시 데이터 손상

**문제:** `.enc` 파일 순차 재암호화 중 크래시 시 일부는 새 PW, 일부는 이전 PW로 혼합 상태 → 복호화 불가.

**결정:** 임시 파일 + 원자적 교체
- 각 파일을 `*.enc.new`로 먼저 작성 완료 후 `rename(*.enc.new → *.enc)` 교체
- 크래시 시 `*.enc.new` 자동 정리, 기존 `*.enc`(이전 PW) 유지

**반영:** `03-account.md`

---

### D-03. 초대 코드 생성자 ≠ 승인자일 때 친구 등록 대상

**문제:** A가 코드 생성, B가 승인 시 피초대자(C)와 친구 등록되는 쪽이 A인지 B인지 불명확.

**결정:** 승인자 기준 + 코드 생성자에게 알림
- B(승인자)와 C(피초대자)가 자동 친구 등록
- A(코드 생성자)의 피드에 `[알림] C가 입장했습니다` 표시 → `/add`로 수동 추가 가능
- InviteRequest에 코드 생성자 PeerId 포함

**반영:** `04-friends.md`, `06-invite.md`, `08-protocol.md`

---

### D-04. 동시 승인으로 인한 방 키 중복 수신

**문제:** GossipSub 전파 지연으로 두 멤버가 동시에 승인 → 피초대자가 InviteResponse(방 키)를 2회 이상 수신.

**결정:** 피초대자 측 멱등성 처리
- 방 키 첫 수신 즉시 입장 완료 상태로 전환
- 이후 동일 방 InviteResponse 무시 (방 키는 고정값이므로 중복 수신 결과 동일)

**반영:** `06-invite.md`

---

### D-05. DHT PUT 초대 코드 등록 값 위조 가능성

**문제:** 초대 코드 등록 시 일반 DHT PUT 사용 → 악의적 DHT 노드가 값(방 내부 ID)을 위조 가능.

**결정:** 등록 값에 Ed25519 서명 추가
- 등록 값: `방 내부 ID + Ed25519 서명(생성자 개인키)`
- 피초대자가 생성자 공개키(PeerId 파생)로 서명 검증
- 검증 실패 시 해당 응답 폐기, 다른 DHT 노드에서 재조회

**반영:** `06-invite.md`, `07-network.md`

---

### D-06. 방 수명 만료 멤버 간 시계 불일치

**문제:** 각 클라이언트가 로컬 시계로 독립 판단 → A는 만료, B는 유효 상태 공존 가능.

**결정:** 현행 유지 + 명시적 허용
- 완전 탈중앙 구조의 의도적 설계로 문서화
- NTP 동기화 환경 기준 오차 수초 이내 → 방 수명(최소 1일) 대비 무의미
- 불일치는 허용, 보안 영향 없음

**반영:** `05-room.md`

---

### D-07. 방 입장 중 방 수명 만료 발생

**문제:** 만료 체크가 "앱 실행 시 및 방 목록 진입 시"에만 수행 → 입장 중 만료 시 아무 처리 없음.

**결정:** 입장 중 1분 간격 체크 + 기능 비활성화 (강제 퇴장 없음)
- 만료 감지 시 피드에 알림, 상태바에 `만료됨` 표시
- 채팅 입력창 비활성화, `/quit` 제외 모든 명령어 비활성화
- 이미 진행 중인 다운로드·시딩은 그대로 유지 (새로 시작 불가)

**반영:** `05-room.md`, `12-tui.md`

### D-08. 방 전환 시 진행 중인 다운로드 처리

**문제:** 초대 수락 또는 `/quit`으로 방을 나갈 때 진행 중 다운로드 처리 미정의.

**결정:** 자동 일시정지 + 재입장 시 자동 재개
- 방 퇴장 시 진행 중 다운로드 자동 일시정지 (`.bf` 파일로 상태 보존)
- 해당 방 재입장 시 자동 재개
- 시딩과 동일한 처리로 일관성 유지

**반영:** `05-room.md`, `10-file-transfer.md`

---

### D-09. 첫 복귀자 BitfieldResponse 권위 문제

**문제:** 전원 오프라인 후 첫 복귀자(A)가 stale한 BitfieldResponse를 제공할 수 있음 → "누구의 정보가 권위 있는가" 불명확.

**결정:** 최종 일관성(eventual consistency) 채택 — 토렌트 방식 그대로
- BitfieldRequest는 임의의 1개 피어에게 전송 (초기 상태 파악)
- 이후 GossipSub BitfieldUpdate로 자연 수렴
- 단기 불일치 허용, 중앙 권위 없음

**반영:** `08-protocol.md`

---

### D-10. 방 미입장 중 초대 수락 후 나머지 대기 초대 처리

**문제:** 메인 메뉴에서 초대 3건 대기 중 1번 수락 시 나머지 2, 3번 처리 미정의.

**결정:** TTL 잔여 초대를 채팅/파일 피드로 이전
- 수락 후 방 입장 시 나머지 대기 초대는 자동 거절되지 않고 피드로 이전
- 기존 방 입장 중 초대 수신 흐름과 동일하게 처리 (`[초대]` 피드 + `/accept <번호>`)

**반영:** `06-invite.md`

---

### D-11. 방 키 전달 폴백 시 승인 기록 검증 신뢰성

**문제:** 폴백 시 GossipSub 승인 기록을 못 받은 멤버는 검증 불가.

**결정:** GossipSub 미수신 시 재승인 팝업 (핵심은 파일 전송)
- 승인 기록 보유 시 즉시 방 키 전달
- 미수신 시 일반 승인 팝업 표시 (TTL 내 재승인 가능)
- 재승인 팝업 1회는 허용 가능한 UX 비용 (파일 전송이 핵심)

**반영:** `06-invite.md`

---

### D-12. 인트라넷 모드에서 친구 초대 시 DHT 조회

**문제:** 인트라넷 모드는 외부 DHT 미사용인데 친구 초대가 "PeerId로 DHT 조회"를 요구.

**결정:** 로컬 DHT 조회
- 인트라넷 모드의 Kademlia DHT는 로컬 피어들로 구성된 내부망 DHT로 동작
- 친구 초대 흐름 동일, 외부망 미접촉
- 다른 서브넷 피어: 수동 주소로 먼저 연결 → 친구 등록 → 로컬 DHT 친구 초대

**반영:** `06-invite.md`, `07-network.md`

---

### D-13. 앱 재시작 시 미완료 다운로드 자동 재개 기준

**문제:** 최대 동시 다운로드 수 3, 미완료 파일 4개 이상 시 자동 재개 기준 미정의.

**결정:** 이전 우선순위 순으로 최대 N개 자동 재개
- 이전 우선순위 순서 그대로 복원
- 상위 N개(최대 동시 다운로드 수 설정값, 기본 3)만 자동 재개
- 나머지는 대기 상태, 슬롯 생기면 순서대로 자동 진입

**반영:** `10-file-transfer.md`

## 중간 심각도

### D-14. 수동 seed-pause 후 방 퇴장 → 재입장 시 자동 재개 덮어쓰기

**문제:** "재입장 시 자동 시딩 재개"가 수동 일시정지 상태를 덮어쓰는지 불명확.

**결정:** 수동 상태 우선 — 자동/수동 일시정지 구분
- `자동 일시정지` (방 퇴장): 재입장 시 자동 재개
- `수동 일시정지` (`/seed-pause`): 재입장 시 유지, 자동 재개 안 함
- 다운로드도 동일하게 적용

**반영:** `05-room.md`, `10-file-transfer.md`

---

### D-15. 거절(Reject)이 3회 실패 카운트에 포함되는지

**문제:** "3회 실패 시 차단"의 실패 기준(코드 오류인지 거절인지) 미정의.

**결정:** 코드 입력 오류만 카운트 (brute-force 방어 목적)
- 방 멤버의 거절은 카운트 제외, TTL 내 재시도 무제한
- 잘못된 코드 입력 3회 시에만 차단

**반영:** `06-invite.md`

---

### D-16. 계정 삭제 후 잠금 파일 및 앱 상태

**문제:** 계정 삭제 후 앱이 종료되는지, 로그인 화면으로 복귀하는지 미정의. 계정 삭제 UI 흐름 없음.

**결정:** 삭제 후 로그인 화면 복귀 (앱 종료 아님) + 계정 삭제 UI 추가
- 잠금 파일은 앱 실행 중이므로 유지 (정상)
- 로그인 화면 `[3] 계정 삭제` 선택 → PW 확인 → 확인 메시지 → 삭제 → 로그인 화면 복귀
- 계정 등록 화면 UI도 함께 추가

**반영:** `03-account.md`, `12-tui.md`

### D-17. 방 목록 피어 수 실시간 조회인지 캐시인지

**문제:** 방 목록의 `peers: N` / `오프라인` 값이 실시간 조회인지 캐시인지 미정의.

**결정:** 캐시 즉시 표시 + 백그라운드 갱신
- 화면 진입 즉시 이전 캐시 값 표시
- 백그라운드에서 DHT Provider Records 조회, 완료 시 자동 갱신
- 조회 중인 방: `확인 중...` 표시

**반영:** `05-room.md`, `12-tui.md`

### D-18. FileRemove 수신 시 다운로드 중인 피어 처리

**문제:** 공유자가 `FileRemove`를 브로드캐스트할 때 다운로드 중인 피어의 처리 미정의.

**결정:** 토렌트 방식 그대로 다운로드 계속 진행
- FileRemove = "발신자가 더 이상 시딩하지 않음", 파일 자체 소멸 아님
- 발신자 bitfield 제거, 다른 피어의 청크로 계속 수신
- 피드에 `[알림] {파일명} 공유가 철회됐습니다.` 표시
- 모든 피어에서 청크 수신 불가 시 `[⏳]` 대기 상태로 전환

**반영:** `08-protocol.md`, `10-file-transfer.md`

### D-19. TTL 3분 내 폴백 재연결 반복 시 만료 경쟁 조건

**결정:** 폴백 루프에서 매 시도 전 TTL 체크, 만료 시 즉시 중단
- TTL 만료 → 폴백 중단, "초대 코드가 만료됐습니다. 새 초대 코드를 요청하세요." 안내

**반영:** `06-invite.md`

### D-20. 방 이름 파트별 최소 길이 미정의

**문제:** `3~32자` 전체 길이만 있고 `.` 앞/뒤 파트별 최소 길이 미정의.

**결정:** 파트별 최소 2자, 전체 최소 5자
- `.` 앞(이름): 최소 2자, `.` 뒤(접미사): 최소 2자
- 전체 길이: 5~32자

### D-21. 만료된 방이 rooms.enc에 수동 삭제 전까지 잔류

**문제:** 만료 방은 "목록 제거 유도"만 하고 자동 삭제 없음 → 방 키가 로컬에 계속 잔류.

**결정:** 만료 감지 즉시 자동 삭제
- 앱 실행 시 또는 방 목록 진입 시 만료 방 감지 → rooms.enc에서 즉시 제거
- 채팅 로그(`logs/`)는 별도 보존
- 정리 후 `[알림] 만료된 방 N개가 정리됐습니다.` 표시
- 방 목록에 `만료됨` 항목 더 이상 표시 안 됨

**반영:** `05-room.md`, `12-tui.md`

### D-22. 청크 보유 피어 전부 차단 시 다운로드 영구 중단 UI 처리

**문제:** 재요청 가능한 피어 없음 상태에서 UI 표시, 타임아웃 여부 미정의.

**결정:** `[⏳]` 대기 상태로 전환, 타임아웃 없음
- `/downloads`에서 `[⏳]` 대기 상태로 표시
- 피드에 `[알림] {파일명} — 청크를 제공하는 피어가 없습니다. 새 피어 연결을 기다리는 중...` 표시
- 새 피어 접속 시 자동 재개 (토렌트 방식 동일)
- `/cancel`로 사용자 직접 취소 가능

**반영:** `10-file-transfer.md`, `12-tui.md`

### D-23. 방 키 인메모리 잔류 (메모리 zeroize)

### D-24. 인트라넷 에어갭 환경에서 TTL 시계 동기화

**문제:** TTL이 "생성 시점부터 카운트"이면 에어갭 환경에서 시계 편차로 인한 오탐 가능.

**결정:** 피초대자가 앱에 코드를 입력한 시점부터 TTL 카운트
- 생성자-수신자 간 시계 동기화 완전히 불필요
- 인터넷/인트라넷 모드 모두 동일하게 적용
- 사용자 기준: "코드 입력 후 3분 내에 승인받으면 됨"

**반영:** `06-invite.md`, `12-tui.md`
