## 1. 계정

### S-01. 계정 등록

**사전 조건:** 앱 첫 실행 또는 로그인 화면 상태

1. 사용자가 ID/PW 입력 후 `[2] 계정 등록` 선택
2. PW 확인 입력
3. ID 중복 없음 + PW 일치 → Ed25519 키쌍 생성 → PeerId 파생
4. `identity.enc`, `config.enc`, `rooms.enc`, `friends.enc` 생성 (계정 PW로 암호화)
5. `users.json`에 ID 추가
6. `계정이 등록됐습니다.` 표시 후 로그인 화면 복귀

**에러:**
- ID 중복 → `! 이미 사용 중인 ID입니다.` 표시, 재입력 유도
- PW 불일치 → `! 비밀번호가 일치하지 않습니다.` 표시, 재입력 유도

---

### S-02. 로그인

**사전 조건:** 로그인 화면

1. 사용자가 ID/PW 입력 후 `[1] 로그인` 선택
2. `users.json`에서 ID 존재 여부 확인
3. `identity.enc` 복호화 → PW 검증
4. `lock` 파일 생성 (현재 PID 기록)
5. 메인 메뉴로 진입

**에러:**
- ID 없음 또는 PW 불일치 → `! ID 또는 비밀번호가 올바르지 않습니다.` 표시

---

### S-03. 비정상 종료 후 재실행 (stale lock)

**사전 조건:** 이전 실행이 크래시로 종료되어 `lock` 파일 잔류

1. 앱 실행 → `lock` 파일 존재 확인
2. 파일 내 PID로 해당 프로세스 생존 여부 OS 확인
3. 프로세스 죽어있음(stale) → `lock` 파일을 현재 PID로 교체
4. 정상 실행 → 로그인 화면

**에러:**
- PID 살아있음 → `앱이 이미 실행 중입니다.` 안내 후 종료
- PID 확인 실패(권한 문제 등) → `앱이 이미 실행 중이거나 비정상 종료됐습니다. ~/.chatapp/lock 파일을 삭제 후 재시도하세요.` 안내 후 종료

---

### S-04. 비밀번호 변경

**사전 조건:** 설정 → 프로필 → 현재 PW 확인 후 진입

1. 현재 PW로 모든 `.enc` 파일 복호화
2. 새 PW 입력 → Argon2id → 새 암호화 키 유도
3. 각 파일을 `*.enc.new`로 먼저 작성 완료
4. 전부 완료 후 `*.enc.new → *.enc` 순차 rename (원자적 교체)
5. `비밀번호가 변경됐습니다.` 표시

**에러 (변경 중 크래시):**
1. 재실행 시 `*.enc.new` 파일 존재 감지
2. `*.enc.new` 자동 삭제
3. 기존 `*.enc`(이전 PW) 유지 → 이전 PW로 정상 로그인 가능

---

### S-05. 닉네임 변경

**사전 조건:** 설정 → 프로필 또는 채팅/파일 화면에서 `/nick <새닉네임>`

1. 닉네임 변경 → `config.enc` 갱신
2. 별도 브로드캐스트 없음
3. 이후 채팅 메시지 발신 시 ChatMessage에 새 닉네임 포함 → 다른 피어들이 자연히 갱신

---

### S-06. 계정 삭제

**사전 조건:** 로그인 화면

1. ID/PW 입력 후 `[3] 계정 삭제` 선택
2. PW 검증 → `! {ID} 계정을 삭제할까요?` 확인
3. `y` 입력 → `~/.chatapp/users/{user_id}/` 전체 삭제
4. `users.json`에서 ID 제거
5. 시딩 즉시 중단
6. `계정이 삭제됐습니다.` 표시 → 로그인 화면 복귀 (앱 종료 아님, lock 파일 유지)

**참고:**
- `~/downloads/`의 파일(부분 다운로드 + `.bf` 포함)은 삭제되지 않음 — 재개 불가 상태로 로컬 유지
- 해당 계정이 유일한 시더였던 파일은 다른 멤버 보유 청크만 남고 나머지 자연 소멸

## 2. 방

### S-07. 방 만들기

**사전 조건:** 메인 메뉴

1. `[1] 방 만들기` 선택
2. 방 이름 입력 (형식: `이름.접미사`, 5~32자)
3. 수명 선택 (기본 1일)
4. 랜덤 고유 ID 생성 → 방 키 생성 (AES-256-GCM)
5. DHT Provider Records에 방 내부 ID로 등록
6. `rooms.enc` 갱신 (방 키 + 내부 ID + 생성 시각 + 수명 저장)
7. 채팅/파일 화면으로 진입

**에러:**
- 방 이름 형식 위반 → `! 허용 문자: 영문, 숫자, -, .` 표시, 재입력 유도

---

### S-08. 방 목록 조회 및 재접속

**사전 조건:** 메인 메뉴

1. `[2] 방 목록` 선택
2. 만료된 방 있으면 즉시 자동 삭제 → `[알림] 만료된 방 N개가 정리됐습니다.` 표시
3. 화면 진입 즉시 캐시 값(`peers: N` 또는 `오프라인`) 표시
4. 백그라운드에서 DHT Provider Records 조회 → 조회 중인 방은 `확인 중...` 표시
5. 조회 완료 시 자동 갱신
6. 방 선택 → Enter → rooms.enc에서 방 키 복호화 → 별도 승인 없이 채팅/파일 화면 진입

---

### S-09. 방 삭제

**사전 조건:** 방 목록 화면

1. 방 선택 → `D` 키
2. `! {방이름}을 삭제할까요? (y/n)` 확인
3. `y` → 해당 방 rooms.enc에서 제거 (방 키 포함 모든 관련 데이터)
4. 방 목록에서 즉시 제거

**참고:**
- 채팅 로그(`logs/`)는 별도 보존

---

### S-10. 방 수명 만료 (방 목록 진입 시)

**사전 조건:** 방 목록 화면 진입

1. 만료된 방 감지 → rooms.enc에서 자동 삭제
2. `[알림] 만료된 방 N개가 정리됐습니다.` 표시
3. 방 목록에 만료된 방 미표시

---

### S-11. 방 수명 만료 (입장 중)

**사전 조건:** 채팅/파일 화면 입장 중

1. 1분 간격 만료 체크 → 만료 감지
2. 피드에 `[알림] 이 방의 수명이 만료됐습니다. /quit 으로 퇴장하세요.` 표시
3. 상태바에 `만료됨` 표시
4. 채팅 입력창 비활성화, `/quit` 제외 모든 명령어 비활성화
5. 이미 진행 중인 다운로드·시딩은 그대로 유지
6. `/quit` 입력 → 방 퇴장 → 메인 메뉴
7. 다음 방 목록 진입 시 해당 방 자동 삭제

---

### S-12. 오프라인 상태로 방 재활성화

**사전 조건:** 방 목록에서 `오프라인` 표시 방 선택

1. 방 선택 → Enter
2. 온라인 피어 없음 → rooms.enc 기준 파일 목록 표시
3. 상태바에 `마지막 동기화: N일 전` 표시
4. DHT Provider Records에 자신을 등록
5. (이후 다른 피어 접속 시) BitfieldRequest → BitfieldResponse 수신 → rooms.enc 갱신 → 상태바 정상 복귀

## 3. 초대

### S-13. 인터넷 모드 — 초대 코드 생성 및 입장 (정상)

**사전 조건:** 초대자(A)가 채팅/파일 화면 입장 중. 피초대자(C)가 앱 실행 중.

**[A — 초대 코드 생성]**
1. A가 `/invite` → `[1] 초대 코드 생성` 선택
2. 초대 코드 생성 → `hash(코드)`를 DHT에 등록 (값: 방 내부 ID + Ed25519 서명)
3. A가 C에게 방 URL + 초대 코드를 외부 채널(카톡 등)로 전달

**[C — 입장]**
4. C가 메인 메뉴 → `[3] 초대 코드로 입장`
5. 방 URL 입력 → DHT 조회 → 방 1개 매칭 → 코드 입력 단계로
6. 초대 코드 입력 → `hash(코드)`로 DHT 조회 → 서명 검증 성공 → 방 내부 ID 확인
7. 온라인 멤버에게 InviteRequest 전송 (방 내부 ID + A의 PeerId 포함)
8. 방 멤버(B)의 화면에 승인 팝업 표시 (C의 PeerId 핑거프린트 포함)
9. B가 승인 → InviteResponse(방 키) 전송 + GossipSub 브로드캐스트
10. C가 방 키 수신 → rooms.enc 갱신 → 채팅/파일 화면 진입
11. 초대 코드 소멸
12. B와 C 자동 친구 등록
13. A의 피드에 `[알림] C가 입장했습니다` 표시

---

### S-14. 인터넷 모드 — 같은 URL에 여러 방 선택

**사전 조건:** 동일 URL에 방이 2개 이상 DHT 등록된 상태

1. C가 방 URL 입력 → DHT 조회 → 복수 매칭 감지
2. 방 내부 ID 앞 8자리 + `#identifier` 목록 표시
3. C가 ↑↓ 이동 후 Enter로 원하는 방 선택
4. 이후 S-13의 코드 입력 단계부터 동일

---

### S-15. 인터넷 모드 — 초대 코드 오입력 차단

**사전 조건:** 코드 입력 단계

1. C가 잘못된 코드 입력 → DHT 서명 검증 실패 또는 코드 불일치
2. 실패 카운터 +1
3. 3회 누적 실패 → `! 코드 입력 횟수를 초과했습니다.` 표시 후 차단
4. TTL 내라도 재시도 불가

---

### S-16. 인터넷 모드 — TTL 만료

**사전 조건:** 코드 입력 후 승인 대기 중 또는 폴백 재시도 중

1. 코드 입력 시점부터 3분 경과
2. `! 초대 코드가 만료됐습니다. 새 초대 코드를 요청하세요.` 표시
3. 진행 중인 폴백 즉시 중단

---

### S-17. 방 키 전달 실패 → 폴백 (GossipSub 기록 보유)

**사전 조건:** B가 승인했으나 C가 10초 내 수신 확인 없음

1. B가 방 키 전달 실패로 간주
2. C가 다른 온라인 멤버(D)에게 자동 재연결
3. TTL 체크 → 유효 → D에게 InviteRequest
4. D는 GossipSub 승인 기록 보유 중 → 추가 팝업 없이 즉시 방 키 전달
5. C가 방 키 수신 → 정상 입장

---

### S-18. 방 키 전달 실패 → 폴백 (GossipSub 기록 미수신 → 재승인)

**사전 조건:** B가 승인했으나 GossipSub 전파 전에 C가 D에게 재연결

1. D는 GossipSub 승인 기록 미수신 → 일반 승인 팝업 표시
2. D가 승인 → 방 키 전달
3. C가 방 키 수신 → 정상 입장

---

### S-19. 방 키 전달 실패 → 폴백 중 TTL 만료

**사전 조건:** 폴백 재시도 반복 중

1. 매 재연결 시도 전 TTL 체크
2. TTL 만료 감지 → 폴백 즉시 중단
3. `! 초대 코드가 만료됐습니다. 새 초대 코드를 요청하세요.` 표시

---

### S-20. 동시 승인 처리

**사전 조건:** B와 D가 거의 동시에 승인 버튼 클릭

1. C가 InviteResponse(방 키)를 B와 D로부터 중복 수신
2. C는 첫 번째 수신 즉시 입장 완료 상태로 전환
3. 이후 동일 방의 InviteResponse 무시 (방 키는 고정값, 중복 수신 결과 동일)
4. 나머지 멤버의 승인 팝업 GossipSub 브로드캐스트로 자동 닫힘

---

### S-21. mDNS 직접 초대 (인트라넷 모드)

**사전 조건:** A가 채팅/파일 화면 입장 중. C가 같은 서브넷에 앱 실행 중.

1. A가 `/invite` → `[1] 주변 피어 탐색` 선택
2. mDNS 탐색 목록 표시 (닉네임#코드 형식)
3. A가 C 선택 → 직접 연결
4. C의 화면에 초대 알림 표시
5. C 수락 → 방 키 전달 (Noise 암호화) → C 입장 완료
6. A와 C 자동 친구 등록

---

### S-22. 친구 초대

**사전 조건:** A가 채팅/파일 화면 입장 중. C가 A의 친구 목록에 존재.

1. A가 `/invite` → `[2] 친구 목록에서 초대` 선택
2. 친구 목록 표시 → C 선택
3. C의 PeerId로 DHT 조회 → C 온라인 확인 → 직접 연결
4. C의 화면에 초대 알림 표시
5. C 수락 → 방 키 전달 → C 입장 완료

**에러:**
- DHT 조회 결과 오프라인 → `! {닉네임}이 현재 오프라인입니다.` 표시 후 초대 취소

---

### S-23. 초대 수신 — 방 미입장 상태 (1건)

**사전 조건:** C가 메인 메뉴 등 방 미입장 상태

1. 초대 수신 → 현재 화면 위에 오버레이 표시
2. `Enter` 수락 → 해당 방으로 입장 → 채팅/파일 화면 전환
3. `D` 거절 → 오버레이 닫힘
4. `Esc` 나중에 → 오버레이 닫힘, TTL 내 메인 메뉴에 알림 유지

---

### S-24. 초대 수신 — 방 미입장 상태 (여러 건)

**사전 조건:** C가 메인 메뉴, 초대 3건 대기 중

1. 번호 목록으로 표시
2. C가 1번 수락 → 해당 방으로 입장
3. 나머지 2, 3번은 자동 거절되지 않고 채팅/파일 피드로 이전
4. 피드에서 `/accept <번호>`로 수락 가능 (TTL 내)

---

### S-25. 초대 수신 — 방 입장 상태

**사전 조건:** C가 채팅/파일 화면 입장 중

1. 초대 수신 → 피드에 `[초대] peer-a가 dev.team 으로 초대했습니다 (/accept 1)` 표시
2. C가 `/accept` 입력
3. 현재 방 자동 퇴장 (다운로드/시딩 자동 일시정지)
4. 초대받은 방으로 입장 → 채팅/파일 화면 전환

---

## 4. 채팅

### S-26. 채팅 메시지 송수신

**사전 조건:** A, B, C 모두 같은 방 입장 중

1. A가 메시지 입력 후 Enter
2. 방 키로 AES-256-GCM 암호화 → ChatMessage(PeerId + 닉네임 + 메시지) 생성
3. GossipSub 브로드캐스트 (StrictSign 자동 서명)
4. B, C가 수신 → 방 키로 복호화 → 피드에 `HH:MM A닉네임 : 메시지` 표시
5. 로컬 로그에 저장

---

### S-27. 닉네임 변경 후 전파

**사전 조건:** A가 방 입장 중

1. A가 `/nick 새닉네임` 입력
2. `config.enc` 갱신
3. 이후 A의 다음 ChatMessage에 `새닉네임` 포함
4. B, C는 A의 다음 메시지 수신 시 자연히 닉네임 갱신
5. 닉네임 변경 직후 단기간 불일치 허용 (의도적 설계)

## 5. 파일 공유

### S-28. 파일 공유 시작

**사전 조건:** A가 채팅/파일 화면 입장 중

1. A가 `/share /path/to/file.zip` 입력
2. 256KB 청크로 분할 + 각 청크 SHA-256 해시 계산
3. FileAnnounce 메타데이터 생성 (방 키로 암호화)
4. GossipSub 브로드캐스트
5. 수신 피어들의 rooms.enc에 파일 메타데이터 저장
6. A는 즉시 시딩 상태로 전환

---

### S-29. 폴더 공유 시작

**사전 조건:** A가 채팅/파일 화면 입장 중

1. A가 `/share /path/to/folder/` 입력
2. 폴더 내 전체 파일 청크 분할 + 해시 계산
3. 디렉토리 구조 포함한 단일 FileAnnounce 생성 (방 키로 암호화)
4. GossipSub 브로드캐스트
5. 수신 피어는 FileAnnounce 하나로 선택적 다운로드 화면 구성 가능

---

### S-30. 파일 전체 다운로드

**사전 조건:** B가 채팅/파일 화면 입장 중, A가 파일 공유 중

1. B가 `/list` → 공유 파일 목록 확인
2. B가 `/download file.zip` 입력
3. 피어별 bitfield 확인 → Rarest-first로 청크 선택
4. 여러 피어에게 동시 ChunkRequest 전송
5. ChunkResponse 수신 → SHA-256 해시 검증 → 디스크 offset에 직접 기록 → `.bf` 플러시
6. 청크 완료 즉시 BitfieldUpdate GossipSub 브로드캐스트 (HAVE 방식)
7. 전체 청크 완료 → 전체 파일 해시 최종 검증
8. 피드에 `[완료] file.zip 다운로드 완료` 표시
9. B는 즉시 시더가 됨

---

### S-31. 폴더 선택적 다운로드

**사전 조건:** B가 채팅/파일 화면 입장 중

1. B가 `/download folder --select` 입력
2. 파일 선택 화면 진입 — 디렉토리 트리 + 체크박스 표시
3. Space로 개별 파일 선택/해제, 폴더 선택 시 하위 일괄 적용
4. 선택 용량 실시간 표시
5. Enter → 선택한 파일만 다운로드 시작
6. 채팅/파일 화면으로 복귀

---

### S-32. 다운로드 일시정지 / 재개

**사전 조건:** 다운로드 진행 중

1. `/pause 1` → 해당 다운로드 일시정지 (`.bf` 현재 상태 보존)
2. `/downloads` 목록에서 `[⏸]` 상태로 표시
3. `/resume 1` → 다운로드 재개 (미완료 청크부터 이어받기)

---

### S-33. 다운로드 취소

**사전 조건:** 다운로드 진행 중 또는 일시정지 중

1. `/cancel 1` 입력
2. 다운로드 중단 + 부분 다운로드 파일 및 `.bf` 파일 삭제
3. 목록에서 제거

---

### S-34. 다운로드 우선순위 조작

**사전 조건:** 다운로드 2개 이상 진행 중

1. `/top 3` → 3번 항목을 최우선순위로 이동
2. `/up 2` → 2번 항목 우선순위 한 단계 올리기
3. `/down 1` → 1번 항목 우선순위 한 단계 내리기
4. 우선순위 순서에 따라 청크 요청 배분 재조정

---

### S-35. 앱 재시작 후 이어받기

**사전 조건:** 다운로드 진행 중 앱 종료 (정상 또는 크래시)

1. 앱 재시작 → 로그인
2. `.bf` 파일로 완료 청크 파악
3. 이전 우선순위 순서 그대로 복원
4. 상위 N개(기본 3)만 자동 재개, 나머지 대기
5. 방 재입장 후 미완료 청크부터 이어받기

---

### S-36. 청크 해시 검증 실패 → 재요청

**사전 조건:** 청크 수신 중

1. ChunkResponse 수신 → SHA-256 해시 검증 실패
2. 해당 피어(P)의 해당 청크 블랙리스트 등록
3. 다른 피어에게 즉시 해당 청크 재요청
4. P의 실패 카운터 +1

---

### S-37. 동일 피어 누적 3회 실패 → 차단

**사전 조건:** 동일 피어(P)로부터 청크 해시 검증 실패 누적 중

1. P의 누적 실패 카운터가 3에 도달 (성공해도 카운터 유지)
2. P 연결 차단 + 로그 기록
3. 차단 정보는 세션 내 유지 (앱 재시작 시 초기화)
4. P가 보유한 청크는 다른 피어에게 요청

---

### S-38. 피어 전원 차단 → 대기 상태

**사전 조건:** 해당 청크를 가진 피어가 전원 차단됨

1. 재요청 가능한 피어 없음
2. 해당 파일 다운로드 `[⏳]` 대기 상태로 전환
3. 피드에 `[알림] {파일명} — 청크를 제공하는 피어가 없습니다. 새 피어 연결을 기다리는 중...` 표시
4. 타임아웃 없음 — 해당 청크 보유 피어 접속 시 자동 재개
5. `/cancel <번호>`로 수동 취소 가능

---

### S-39. FileRemove 수신 중 다운로드 진행

**사전 조건:** B가 A의 파일 다운로드 중, A가 공유 철회

1. A가 `/remove 1` 실행 → FileRemove GossipSub 브로드캐스트
2. 피드에 `[알림] {파일명} 공유가 철회됐습니다.` 표시
3. A의 bitfield 제거 → 이후 A에게는 청크 요청 안 함
4. 다른 피어(C)가 해당 청크 보유 시 C에게 계속 요청 → 다운로드 진행
5. 모든 피어에서 해당 청크 수신 불가 시 `[⏳]` 대기 상태 전환

---

### S-40. 시딩 일시정지 / 재개

**사전 조건:** A가 시딩 중

1. `/seed-pause 1` → 해당 파일 시딩 일시정지 (다른 피어에게 청크 제공 중단)
2. `/seed` 목록에서 `[⏸]` 상태로 표시
3. `/seed-resume 1` → 시딩 재개

### S-41. 시딩 중단

**사전 조건:** A가 시딩 중

- `/remove 1` → 확인 후 시딩 중단 + 목록 제거 (로컬 파일 유지)
- `/remove-all 1` → 확인 후 시딩 중단 + 목록 제거 + 로컬 파일 삭제

### S-42. 방 퇴장 → 재입장 시 다운로드·시딩 재개

**사전 조건:** A가 다운로드·시딩 진행 중 방 퇴장

2. 활성 시딩 → 자동 일시정지
3. 수동 일시정지(`/seed-pause`) 시딩 → 상태 그대로 유지
4. 진행 중인 다운로드 → 자동 일시정지 (`.bf` 보존)
5. 방 목록에서 해당 방 재입장
6. 자동 일시정지된 시딩·다운로드만 자동 재개
7. 수동 일시정지 상태는 유지 (자동 재개 안 함)

## 7. 네트워크

### S-46. 인트라넷 최초 세팅

**사전 조건:** 망분리 환경, 외부망 차단

1. 관리자(A)가 설정 → 네트워크 모드를 `인트라넷`으로 변경
2. A가 자신의 `multiaddr`(IP:Port)를 내부 채널로 공유
3. 신규 참여자(B)가 설정 → 수동 피어 주소 목록에 A의 주소 등록
4. B가 A에 직접 연결 → 로컬 DHT 형성
5. 이후 초대는 로컬 DHT 또는 mDNS로 정상 동작

---

### S-47. 다른 네트워크에서 재접속

**사전 조건:** A가 집 네트워크에서 앱 종료 후 회사 네트워크에서 재실행

1. 앱 실행 → 로그인
2. 방 목록에서 방 선택
3. rooms.enc에서 방 고유 ID 확인 → DHT 조회
4. 현재 온라인인 피어 주소 수신
5. 자동 연결 → 별도 승인 없이 채팅/파일 화면 진입

---

### S-48. 오프라인 입장 → 다른 피어 접속 시 동기화

**사전 조건:** A가 오프라인 상태로 방 입장 (S-12 이후)

1. A가 rooms.enc 기준 파일 목록 표시 중
2. B가 방에 접속
3. A가 B에게 BitfieldRequest 전송
4. B가 BitfieldResponse(전체 파일 목록 + 청크 현황) 응답
5. A의 rooms.enc 갱신 (오프라인 중 추가/삭제된 파일 반영)
6. 상태바 `마지막 동기화: N일 전` 제거 → 정상 상태로 복귀
7. 이후 변경 사항은 GossipSub BitfieldUpdate로 자연 수렴
